# Демо-аккаунты «посмотреть изнутри»

Согласовано: октябрь 2026. Гость с лендинга нажимает «Как спортсмен» или «Как тренер» (вариант A — две кнопки)
и попадает в настоящее приложение с заполненным дневником. Всё можно трогать; через сутки демо удаляется само.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Один общий аккаунт или свой каждому | **Песочница на гостя**: свой временный пользователь | Гости не мешают друг другу, запрещать почти ничего не нужно |
| Откуда данные | **Генератор** по сценарию, даты — от «сегодня» | «Рекорд вчера» всегда вчера; копия из базы устарела бы |
| Кто генерирует | Слушатель Kafka в workout-service (событие `DemoDataRequested`) | Как обычные сервисы: без отдельного воркера и без миграций |
| Аналитика | Не генерируем: каждая тренировка — обычный `WorkoutCompleted`, аналитика считает сама | Одна логика для демо и для настоящих данных |
| Сколько живёт | 24 часа с момента создания | Хватит посмотреть; база не копит мусор |
| Перенос демо в настоящий аккаунт | Нет — регистрация с нуля | Данные демо ненастоящие |
| Пул готовых демо | Не нужен: замер — 3,5–4,5 с (см. ниже); если станет > 5 с — добавим (`SELECT … FOR UPDATE SKIP LOCKED`) | Сначала замерить |

## Как устроено

```
Гость → POST /api/auth/demo {scenario: ATHLETE | COACH}
  user-service (одна транзакция):
    лимиты (IP, всего демо) → пользователь DEMO + профиль + вес за 2 месяца
    [COACH: + 5 клиентов без аккаунта, связи тренер—клиент]
    outbox: UserProfileUpdated, TrainerClientLinked, DemoDataRequested (на каждого человека)
  ← токены сразу (как при регистрации), фронт: «Готовим ваш дневник…»

workout-service ← DemoDataRequested {userId, scenario, recordedBy}
  генератор: тренировки за N недель (одной транзакцией), комплексы, план на неделю
  outbox: WorkoutCompleted × N
analytics-service ← WorkoutCompleted × N → рекорды, плато, перегрузка (уведомления — только за последние 7 дней)
notification-service ← события аналитики → колокольчик (письма не уходят: у демо нет email)

Фронт опрашивает /api/analytics/dashboard, пока он пустой → открывает главную.
```

## Сценарии

- **Спортсмен «Алексей»** (средний уровень, ~5 месяцев, 3 тренировки в неделю): жим растёт с рекордами
  (свежий рекорд — вчера), присед — плато ~4 недели, становая — резкий рост объёма на последней неделе
  (перегрузка), подтягивания, жим стоя; пробежки по выходным; вес тела 82 → 79 кг; 3 комплекса и план на неделю;
  в прошлом месяце достаточно тренировок для отчёта.
- **Тренер «Марина»**: свои тренировки (~2 месяца, 2 раза в неделю) и 5 клиентов без аккаунта — у каждого своя
  метка в «Чей дневник открыть»: Иван — идёт тренировка, Ольга — перегрузка, Пётр — плато, Марат — 12 дней без
  тренировок, Анна — рекорд вчера. Тренировки клиентов записаны тренером (`recorded_by`).

## Генератор (шаг 2) и замеры

- `DemoScenarios` — чистые функции: план тренировок по сценарию от «сейчас». Тест `DemoScenariosTest` проверяет
  сценарии по тем же правилам, что аналитика: у спортсмена плато только в приседе, перегрузка только в становой,
  свежий рекорд — жим (и становая перед перегрузкой); вспомогательные упражнения растут раз в 3 недели, последний
  рост 15–20 дней назад — ни плато (21+), ни «рекорда» (14 дней): спокойные карточки.
- `DemoDataGenerator` — одна транзакция: комплексы, тренировки, план на неделю, события `WorkoutCompleted`.
  Повтор события → у пользователя уже есть тренировки → пропуск. Событие старше часа → пропуск (перечитали топик —
  не «воскрешаем» удалённых). Упражнения нет в каталоге → пропускаем его, остальное создаём.
- «N дней назад» = ровно N суток + 1,5 часа: аналитика считает дни полными сутками, «рекорд · вчера» не станет «сегодня».
- Замер на стенде (тёплые сервисы): спортсмен (73 тренировки) — главная готова через **3,5–4,5 с**,
  тренер с клиентами (~135 тренировок) — **3,5–5,5 с**. Сразу после перезапуска сервисов — до ~20 с
  (прогрев JVM и подключение к Kafka): экран «Готовим…» должен спокойно ждать до 40 с.
- Вставки пачками (`hibernate.jdbc.batch_size: 50`, `order_inserts`) ускорили генерацию ~на секунду.

## Уборка

- Демо-пользователи — задача в user-service через час после конца демо → `UserDeleted` → каждый сервис чистит своё.
  Проверено на стенде: 25 демо (637 тренировок, 1 525 строк аналитики, 46 уведомлений, связи тренера в трёх
  копиях) → после удаления 0 строк во всех базах.
- **Outbox во всех сервисах** (`common-outbox`, `OutboxCleanup`): отправленные события старше 7 дней удаляются раз в час
  (`app.outbox.retention`). Раньше таблицы росли бесконечно; с демо — ~75 событий на одно демо спортсмена.

## Фронт (шаг 3)

- Лендинг: отдельная рамка «Посмотреть изнутри — без регистрации» с кнопками **«Демо спортсмена»** и **«Демо тренера»**
  (не «Как спортсмен» — иначе кажется, что кнопка создаёт аккаунт). Ошибка 429 — текстом под кнопками.
- `/demo` — «Готовим ваш дневник…»: опрос сводки раз в секунду; готово, когда отпечаток (сводка, у тренера ещё
  сигналы всех клиентов — у каждого уже есть тренировки) не меняется 3 опроса подряд. Через 15 с — «чуть дольше
  обычного», через 40 с — открываем как есть. Замер с клика до главной: 7,5–8 с (из них ~2 с — проверка, что досчитано).
- Полоса «ДЕМО · удалится через 23 ч · Зарегистрироваться» над всеми экранами. Регистрация — с нуля (выход из демо).
- В демо скрыты: напоминания на почту, «Удалить аккаунт» (вместо «Выйти» — «Выйти из демо» → лендинг),
  «Передать аккаунт» клиенту. Плашки про email нет сама собой — у демо нет email.
- Метка демо в `sessionStorage`: вход пропал (сутки прошли) → лендинг с «Демо закончилось…», а не форма входа.
  В новой вкладке метки нет — там обычная форма входа.

## Ограничения в демо

У демо-пользователя нет email и пароля (`auth_provider = DEMO`). Запрещено (сервер отвечает 403, фронт прячет):
- смена email, подтверждение email, «Забыли пароль?» — нет почты;
- «Удалить аккаунт» — вместо него просто «Выйти из демо» (данные удалятся по расписанию);
- «Передать аккаунт» клиенту — иначе из демо получится настоящий аккаунт;
- письма — не уходят (нет email → в журнале уведомлений SKIPPED, в колокольчике видны).

Всё остальное — как у обычного пользователя: записывать тренировки, править план, включать режим тренера,
заводить клиентов (удалятся вместе с демо).

## Защита от злоупотреблений

- Не больше 5 демо в час с одного IP (в памяти user-service; IP — первый адрес в `X-Forwarded-For`,
  его ставит Caddy) → 429 «Слишком много демо, попробуйте через час».
- Не больше 200 живых демо одновременно → 429 «Сейчас много гостей, попробуйте позже».
- Капчи нет.

## Окончание демо — без «сирот»

Проблема: удалили пользователя, а у браузера ещё 15 минут живёт access-токен — запрос с ним создал бы
тренировку «ничью» (в других сервисах её уже никто не удалит).
Решение: после `demo_expires_at` refresh-токен больше не обменивается (401 → фронт выходит на лендинг),
а удаление по расписанию — только через час после истечения (> срока access-токена).
К моменту удаления ни одного рабочего токена у демо нет.

Удаление — задача по расписанию раз в 10 минут, тем же путём, что «Удалить аккаунт»
(`UserDeleted` → каждый сервис чистит своё; клиенты демо-тренера удаляются вместе с ним).

## Все случаи, которые проверяем

| Ситуация | Что происходит |
|---|---|
| Гость нажал кнопку дважды подряд | Фронт блокирует кнопку; второй запрос — второе демо (лимит IP это ограничит) |
| Генерация ещё идёт, гость на главной | Экран «Готовим…» опрашивает сводку; через 30 с — открываем как есть |
| Демо-тренер заводит своего клиента | Обычный клиент без аккаунта — удалится вместе с демо-тренером |
| Демо-спортсмен включил «Я тренер» | Можно; клиенты удалятся вместе с ним |
| Попытка «Передать аккаунт» в демо | 403 |
| Попытка сменить email / удалить аккаунт | 403, на фронте этих кнопок нет |
| Гость нажал «Зарегистрироваться» | Выход из демо → обычная регистрация с нуля |
| Гость вернулся через 25 часов | refresh отклонён → лендинг; данные удалятся по расписанию |
| Демо истекло, пока гость в приложении | Через ≤ 15 мин refresh не сработает → лендинг с «Демо закончилось» |
| Сервис упал посреди генерации | Транзакция откатилась целиком; событие в Kafka обработается заново |
| Сервис упал после генерации, но до подтверждения в Kafka | Событие придёт ещё раз → тренировки уже есть → пропуск, без дублей |
| Топик перечитали с начала (новая группа читателей) | События старше часа пропускаются — удалённые демо не «воскреснут» |
| Упражнение переименовали в каталоге | Генератор пропустит его, остальное создаст |
| Kafka повторила `DemoDataRequested` | То же: генерация идемпотентна |
| Сто гостей одновременно | Очередь: генерация последовательная; лимит 200 живых демо и 5/час на IP |
| Демо в итогах месяца / рассылках | Писем нет (нет email); в статистику приложения демо не попадают |
| Удаление демо-тренера | Сначала его клиенты без аккаунта, потом он сам (`UserDeleted` на каждого) |

## Шаги

1. **user-service** — пользователь DEMO, `POST /api/auth/demo`, лимиты, сценарии людей (профиль, вес, клиенты тренера),
   событие `DemoDataRequested`, запреты, окончание и удаление по расписанию.
2. **workout-service** — генератор тренировок по сценариям (идемпотентно), комплексы и план.
3. **Фронт** — две кнопки на лендинге, «Готовим ваш дневник…», полоса «ДЕМО · удалится через сутки ·
   Зарегистрироваться», скрытые запрещённые действия, «Демо закончилось».
4. **Проверка на стенде** — оба сценария, все случаи из таблицы, замер времени готовности.
