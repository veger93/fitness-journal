# Аккаунты тренеров — дизайн

Согласовано: октябрь 2026. Работаем в интеграционной ветке `feature/trainer`: каждый шаг — своя ветка
и PR **в `feature/trainer`** (CI проверяет, прод не трогаем). В конце — один PR `feature/trainer` → `main` и деплой.

## Идея

Тренер ведёт клиентов в Vegas сам — клиенту не нужно ни ставить приложение, ни регистрироваться
(«я пришёл тренироваться, а не в телефон смотреть»). Если клиент захочет вести дневник сам — тренер
**передаёт ему аккаунт** со всей историей.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Кто тренер | Обычный пользователь с переключателем «Я тренер» в профиле | Тренер и сам тренируется — второй аккаунт не нужен |
| Клиент без регистрации | Полноценный пользователь в `users` без email и пароля («ведомый», `auth_provider = NONE`) | Все тренировки с первого дня лежат под **id клиента** — передача аккаунта не требует переноса данных между сервисами |
| Что вводит тренер | Имя — обязательно; вес, рост, уровень, телефон — по желанию | Данные человека, который ещё не давал согласия: чем меньше, тем лучше. Согласие — при передаче аккаунта |
| Где телефон | В связи «тренер — клиент», а не в аккаунте | Это записная книжка тренера; уйдёт клиент — уйдёт и запись |
| Сколько тренеров у клиента | Один | Несколько — не делаем вообще |
| Слияние с уже существующим аккаунтом клиента | Не делаем | Редкий случай, сложная логика |
| Свой аккаунт → к тренеру по приглашению | Позже (если понадобится) | Сначала основной сценарий: тренер заводит клиента |

## Жизненный цикл клиента

```
Тренер создаёт клиента ──► ВЕДОМЫЙ (входа нет, всё ведёт тренер)
        │
        │  «Передать аккаунт» → одноразовая ссылка / QR-код
        ▼
Клиент открывает ссылку, придумывает email + пароль ──► САМОСТОЯТЕЛЬНЫЙ
        │
        ├─ «Продолжаю с тренером» → тренер дальше видит и записывает
        └─ «Дальше сам»           → связь закрыта, доступ тренера пропадает, статистика у клиента
```

Клиент может отключить тренера в профиле в любой момент. После передачи тренер не может поменять клиенту
email/пароль — хозяин аккаунта клиент.

## Передача аккаунта (шаг 4)

- Тренер: карточка клиента → «Передать аккаунт» → QR-код (в зале — отсканировать с телефона тренера) и «Скопировать ссылку».
- Ссылка `vegas-fit.ru/claim/<токен>`: токен случайный, одноразовый, в БД — только SHA-256 хеш (как refresh-токены),
  живёт 7 дней; новая ссылка отменяет старую.
- Клиент видит «Тренер Сергей передаёт тебе дневник: 34 тренировки, 7 рекордов», вводит email и пароль,
  соглашается на обработку данных и выбирает «с тренером / дальше сам».
- После этого — обычный аккаунт: `auth_provider = LOCAL`, событие `UserRegistered` (notification-service узнаёт email).

## Доступ тренера к данным клиента (шаг 2)

Тренер шлёт обычные запросы (`/api/workouts/...`, `/api/analytics/...`) с заголовком **`X-Client-Id: <id клиента>`**.
`TrainerAccessFilter` (модуль `common-trainer-access`) после проверки токена смотрит в копию связей:
это клиент этого тренера? Да — запрос выполняется **как будто его сделал клиент** (в Jwt `sub` = клиент,
а тренер — в стандартном поле `act`, RFC 8693). Нет — 403. Поэтому ни один существующий эндпоинт не пришлось дублировать.

Связи живут в user-service, workout и analytics держат копию из Kafka (`TrainerClientLinked` в топике user-events,
своя consumer group `<сервис>.trainer-links`) — проверка доступа не ходит по сети в user-service на каждый запрос
(паттерн event-carried state transfer).

У тренировки есть `recorded_by` — кто записал (null — сам клиент, иначе тренер); во фронт уходит `recordedByTrainer`.

Переключение «Я / клиент» — только на фронте (есть заголовок или нет). У тренера и клиента свои тренировки,
поэтому тренер может вести свою, пока у клиента не завершена, — но фронт напомнит: «У Ивана идёт тренировка».

## Шаги

1. **user-service** — режим тренера, ведомые клиенты, таблица `trainer_clients`, API тренера, событие `TrainerClientLinked`.
2. **workout- и analytics-service** — копия связей из Kafka, запросы «за клиента» с проверкой доступа, поле «кто записал».
3. **Фронт** (вариант A «переключатель в шапке») — «Я ▾» в шапке → окно «Чей дневник открыть» (я, клиенты,
   у кого не завершена тренировка) и «Новый клиент»; в режиме клиента — оранжевая полоса «Иван · ✕ К себе»
   и оранжевая капсула в нижней панели; все экраны те же, запросы уходят с `X-Client-Id`
   (`api/client.ts`, `trainer/ActingClientProvider.tsx`). Мягкое напоминание «Иван: тренировка идёт → Вернуться».
   «Профиль» в режиме клиента — карточка клиента (имя, телефон). Переключатель «Я тренер» — в своём профиле.
4. **Передача аккаунта** — в режиме клиента «Профиль» → «Передать аккаунт»: ссылка на 7 дней + QR (библиотека `qrcode`);
   `/claim/:token` — клиент вводит email, пароль, выбирает «с тренером / дальше сам», даёт согласие и сразу входит
   (дальше онбординг: пол и год рождения). «Дальше сам» и «Отключить тренера» в профиле клиента закрывают связь —
   событие `TrainerClientUnlinked`, копии в workout/analytics её удаляют, у тренера клиент пропадает.
5. **Уведомления** — сводка тренеру, письмо клиенту после передачи.

Нужно до передачи аккаунта в проде: подтверждение email (см. `ideas.md`) — иначе клиент не восстановит пароль.
